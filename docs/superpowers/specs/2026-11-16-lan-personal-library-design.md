# 局域网个人资料库共享（LanDocShare）设计方案

- 日期：2026-11-16
- 状态：待评审 / 待批准
- 作者：与库主人（陈鋆）讨论后成文

---

## 1. 背景与意图（为什么做）

现在院里只有一份"共享资料库"：陈鋆把自己 2005–2025 年的工作文档转成 Markdown，建了 FTS5 索引，跑一个只读检索服务（`F:\md_share\share_server.py`，端口 8766），同事装一个 skill（`chenjun-md-remote-search`）就能检索命中文档片段和文档内表格。

这套东西被证明是有用的，但它是**单人版**：库只有一份、名单只有一个人改、全院同事的 IP 要手工登记在 `share_people.json` 里，任何同事想贡献自己的资料，都要把文件拷给陈鋆，走一遍他的转换流程。

本次要解决的，是把这套东西从"一个人的库"变成**"每个人都能自己建、彼此能查"**：部门同事在自己电脑上双击一个软件，选中自己要共享的文件夹，剩下的（加密文档转换、建索引、开机自启、对院内提供服务）全自动；其他同事用同一个 skill，就能检索到院里所有人共享的库。

**成功的样子**：某个同事想找"别人写过的那份类似方案"，打开 AI 说一句"查一下院里有没有 XX 的资料"，3 秒内拿到命中清单和片段，不需要问人、不需要翻共享盘。

---

## 2. 目标 / 非目标 / 反面目标

### 目标（本次交付）
1. 同事**零命令行、零 Python 环境**：一个 exe + 一个"选择文件夹"的向导，装完即用，随开机自启。
2. 加密的 Office 文档（单位透明加密，密文头 `17DA5FA01633CD9A`）**不依赖解密工具**也能转成可检索文本。
3. 同事之间**互相发现**：一个轻量登记中心 + 客户端本地缓存。
4. 检索体验：一次查询可覆盖"全院所有在线库"，结果按相关度合并，每条带"来自谁、哪个文档"。
5. 权限默认对规划院内网开放，库主人可随时收紧或停止共享。

### 非目标（本次不做）
- 不提供全文下载、原文导出（保持"只给片段 + 表格数值"的边界）。
- 不做跨库写入、评论、收藏、协同编辑。
- 不做中心代理检索（见第 4 节的方案比较，明确否决）。
- 不做 `.xls/.xlsx/.et` → md（用户已明确本轮不需要）。
- 不做移动端、不做 Web 管理后台。
- 不做文档在线预览渲染。

### 反面目标（做到这些就算失败）
- **为了覆盖率把解密工具分发到全部门**，让产品变成"绕过加密管控的分发器"（合规红线，见第 6.6 与第 11 节）。
- 需要管理员权限才能日常运行。
- 需要每台机器的用户懂命令行、懂 Python、懂依赖安装。
- 中心一挂全院不可用。
- 建库把整台电脑的私人文件（照片、个人文档）卷进索引，引发投诉。

## 3. 前提事实（本次实测，2026-11-16）

这些事实推翻了几个常见假设，实现者必须以它们为准。

### 3.1 单位透明加密的判定规律：**取决"谁写"，不取决后缀**
- 加密文件前 4 字节为 `17DA5FA0`（前 8 字节 `17da5fa01633cd9a`），密文比明文大 1024 字节。
- **白名单进程（winword / excel / powerpnt / wps / et / wpp / acad / acrobat / ACDSee）读文件时被驱动透明解密 → 拿到明文；非白名单进程（python、pdftotext、git bash）读到的是密文。**
- **白名单进程写文件一律落盘为密文**（实测：WPS 另存 `.txt` 到 `C:\Temp`，文件头仍是 `17da5fa0`）。所以"先用 Office 另存为，再用 python 解析"这条路是死的。
- **python 等非白名单进程写出的文件是明文**（实测：python 写 `.md`、`.docx` 均为标准魔数）。

→ 结论：**文本必须从 Office 进程内存里取出来，由 python 落盘。**

### 3.2 加密 Office 文档 → md 的可行链路（已实测通过）
桌面实测文件：`2026.11.10 乐平下闸蓄水设计自检报告-水文.docx`（密文头 `17da5fa0`）。

1. `python-docx` / `zipfile` 直读 → `BadZipFile`（失败，符合预期）。
2. `Word.Application` 或 `KWPS.Application` COM 以 `ReadOnly=True` 打开 → 成功。
3. `doc.Content.WordOpenXML` 取回 **Flat OPC 字符串**（约 3.3 MB，纯内存）→ 成功；Word 与 WPS 均支持。
4. python 用该字符串重建一个合法 `.docx`（关键：WordOpenXML 的 Flat OPC **不含 `[Content_Types].xml`**，需按各 `pkg:part` 的 `contentType` 自行合成）→ 0.23 s，落盘为明文（头 `504b0304`）。
5. `python-docx` 解析重建件 → 132 段落 / 13 张表，**Heading 1/2/3 样式完好**，表头表体完整。

耗时：首个文档 6.4 s（含 Office 启动），之后 **约 1.0 s 取 XML + 0.4 s 重建解析 ≈ 1.4 s/份**。

### 3.3 加密 PPT → 文本（已实测通过）
`KWPP.Application`（PowerPoint/WPS 演示）打开 → 逐页 `Slides(i).Shapes(j).TextFrame.TextRange.Text`、表格逐格取 → 拼接。实测 `WorkBuddy水文分析实战运用汇报-溪霞水库.pptx`（密文）得到 16.6 KB 文本，分页与表格正常。

### 3.4 加密 PDF：现状最差，只能两条路
实测同一份加密 PDF（`附件1 江西省"十五五"水安全保障规划报告（送审稿）.pdf`，密文，21 页）：

| 打开方式 | 结果 |
|---|---|
| `pdftotext` / `pypdf` / `pymupdf` | ✗ 报"不是 PDF"（密文） |
| Foxit PhantomPDF | ✗ 弹窗「格式错误：不是一个 PDF 文件或该文件已损坏」 |
| WPS PDF（`wpspdf.exe`） | ✗ 弹窗「无法打开文件：不支持打开该类型文件或文件已损坏」 |
| Word 2007（12.0） | ✗ 不支持 PDF |
| Word 2019（16.0） | ⚠ 能打开（走 PDF→Word 转换，需处理"文件转换"对话框与 COM 时序，脆） |
| 伪装名 `acrobat.exe`（现有右键解密工具） | ✅ 一次成功，头恢复 `%PDF-1.7`，pymupdf 读到 21 页 / 8451 字，**文本层完好，不需 OCR** |
| **Adobe Acrobat（真装的 Acrobat DC，`AcroExch.PDDoc`）** | ✅ **最优路径**：`PDDoc.Open` 直接读密文，逐页 `CreateTextSelect(整页 Rect)` + `GetText` 取文本；21 页 **0.8 秒** / 8456 字，文本干净，**不落任何明文副本** |

→ 白名单只认 `acrobat.exe` 这个名字：装了 **Adobe Acrobat（Pro/Std，或 Acrobat DC）** 的机器天然可读；Acrobat Reader 的可执行文件名是 `AcroRd32.exe`、Foxit、WPS PDF 都不行。

**Acrobat 取词的坑（实测）**：`PDTextSelect.GetText(i)` 返回的是**单个字符**（换行也是独立 token），直接 join 会得到逐字断行的碎片，trigram 检索命中率归零。必须用拼接规则（`pdf_conv._join_tokens`）：中文之间不加分隔符、ASCII 之间补空格、空白 token 只保留一个换行。`PDDoc.GetJSObject()` 在 Acrobat DC（Reader 档位）上报 `尚未实现`，不可用；`PDDoc` 也没有 `SaveAs`，`AVDoc` 只有 `PrintPages*`，所以**取文本只能走 `CreateTextSelect`**。

### 3.5 加密文件的真实占比（抽样 G:/I: 4000 份）
- 加密 PDF：1 / 771（0.13%）
- 加密 Office（doc/docx/xls/xlsx）：17 / ~2260（0.4%）
- 其余 docx/xls/doc/pdf 均为标准明文。

→ 加密不是主流量，**但"python 直读在同事机器上是否放行"不稳定**（本机 python 能读大部分明文文件，同事机器可能更严），所以转换层必须"先体检、再选路"。

### 3.6 现有可复用的资产
- `F:\md_share\share_server.py`（22 KB）：只读检索服务、姓名+IP 鉴权、限流、审计、FTS5 查询、目录聚合、表格抽取。**这是"每台库服务"的直接原型。**
- 索引 schema：`documents(rowid, rel_path, title, ext, source_path, src_size, src_mtime, content, indexed_at)` + `documents_fts`（FTS5，`bm25(fts, 10.0, 1.0)`，title 权重 10）+ `meta`。**`documents.content` 已存全文**。
- 运行侧经验：隐藏启动 VBS、看门狗 PowerShell + 计划任务、`netsh advfirewall` 首次放行 8766、`make_share_dist.py` 生成 skill 分发包。
- 本机环境：Python 3.14.0、PyInstaller 6.17、jieba 0.42、pymupdf 1.27、python-docx 1.2、pywin32 可用、sqlite 3.50（FTS5 可用）。

## 4. 方案比较与选择

三个形态的差别在**检索流量与数据落在哪里**。

| | 甲｜中心是目录，检索点对点 | 乙｜中心代理检索 | 丙｜中心汇总全量索引 |
|---|---|---|---|
| 中心存什么 | 姓名/IP/端口/库名/篇数/心跳 | 同甲，但转发所有查询 | 所有库的全文索引 |
| 查询路径 | 客户端直连各库，并发取回后合并 | 客户端→中心→各库→中心→客户端 | 客户端→中心 |
| 隐私 | 查询内容不集中 | **中心能看到所有人查了什么** | **全场明文集中一台机器** |
| 中心故障 | 用缓存名单继续工作 | 全院查询中断 | 全院查询中断 |
| 实现成本 | 中（客户端要做 fan-out） | 中 | 高（要处理增量同步、冲突） |
| 与"个人库"边界 | 守住（数据留在各人机器） | 基本守住 | 冲突 |

**选择：甲。** 理由：① 守住"个人资料库"的产品本质，数据不离开库主人机器；② `share_server.py` 原样就是甲里的库服务，改造量最小；③ 中心只是个电话簿，几百行，坏了有缓存兜底。

乙、丙被否决：乙把查询行为（谁在查什么、查了谁）集中到一台机器，等于凭空造出一个监督点；丙与"库主人关机就查不到"的产品边界直接冲突，且明文汇总本身就是合规灾难。

**建库范围**：同事**手动多选文件夹**（1..N 个，默认空），扫全盘作为高级开关且默认关闭。

## 5. 系统组成

五个部件：

1. **库软件（LanDocShare.exe）** — 每台同事机器一个。托盘常驻，负责：首次向导选文件夹、后台建库/增量更新、本地 FTS5 索引、对院内提供只读检索 API、向中心注册心跳、开机自启。
2. **登记中心（registry）** — 一台常开机器（建议复用 `10.91.1.197`，与现有 8766 服务并存，新端口 8767）。只存元数据，每 60 s 刷新在线状态，下发库名单。
3. **客户端 skill（`lan-lib-search`）** — 装在同事 AI 助手里（pi / ZCode / Claude Code 同一份包）。首次填姓名写 `identity.txt`；查中心拿名单（本地缓存 24 h）；并发 fan-out 查询；合并排序输出。
4. **权限模型** — 库端自己执行（默认 `10.91.0.0/16`），中心只展示状态，不做授权。
5. **分发与升级** — 单 exe 安装包 + 自更新检查；skill 包由中心动态生成（或静态包只改服务器地址）。

## 6. 库软件（每台机器）

### 6.1 运行形态
- **PyInstaller `--onedir`**（不用 onefile：避免每次启动解压几十 MB、也方便 COM/资源定位），产物目录约 60–120 MB。
- 托盘：`pystray` + `Pillow`；菜单项：`显示状态窗口 / 打开库主页（浏览器）/ 我的库（篇数·最后更新）/ 立即重建索引 / 修改建库设置… / 授权名单… / 暂停共享 / 权限设置 / 开机自启（勾选）/ 查看日志 / 退出`。
- **状态窗口**（实施补充，2026-11-17）：托盘之外再给一个 tkinter 小窗，显示状态 / 篇数 / 共享范围 / 服务地址 / 上次扫描，带"打开检索页 / 立即更新 / 暂停共享 / 复制地址"；关窗只隐藏，双击托盘图标再打开；`--autostart` 模式不弹窗。
- **开机自启**：写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（不需要管理员）。软件自身单实例（命名互斥量），重复启动时唤起已运行实例的窗口。
- **无需管理员**：唯一需要提权的是首次加防火墙规则；失败时降级为"提示手动执行命令"，不阻塞建库。
- **端口**：默认 8766；若被占用（例如陈鋆机器上现有服务），自动探测 8766→8768→8769…（**跳过 8767**，那是 registry 的保留端口），并把实际端口写进中心注册。

### 6.2 首次运行向导（≤3 步）
1. 填"我的名字 / 库名称"（默认 `<姓名>的资料库`）。
2. 选文件夹（**多选**，支持拖入）。显示每个文件夹的"预计文档数 / 体积 / 预计耗时"（抽样估算，不等全量扫描）。
3. 选共享范围（默认：`公司内网 10.91.0.0/16`，**网段可在向导里改**；可改：仅指定名单 / 仅本机）。→ 开始建库，托盘显示进度。

> **实施补充（2026-11-17）**：三步合成一屏（少点一次"下一步"）。没有 `config.json` 时托盘启动即弹向导；已建库的从托盘菜单「修改建库设置…」重开（字段预填、按钮变"保存"），改完就地写回运行中的配置、当场生效。估算用 `wizard.estimate_folders`（只 walk + stat，15000 篇封顶，显示"≥ N 篇"）。共享范围三档：内网 / **仅指定名单** / 仅本机；网段一栏可编辑（默认 10.91.0.0/16，实测本机是 10.91.1.0/24 且 10.91.10.x 可路由到——/16 未必只属于本院，要收窄就填本院网段，如 10.91.1.0/24）；名单是网段之上叠一层（`allow_people: 姓名 → 期望 IP`，**按 IP 放行、姓名只作备注**：来源 IP 命中任一登记 IP 即放行，审计记那条的姓名；姓名登记了 IP 时校验一致（防冒名）；IP 留空 = 只能靠报姓名识别，适合 IP 会变的人；回环 `127.0.0.1` 永远放行，主人本机自检不被名单挡住），向导里是一张可增删的姓名/IP 表并支持「从 CSV 导入」（`姓名,IP` 两列），命令行 `people --csv/--set/--remove/--export` 维护、改动即时生效；服务端 `/api/meta` 只回 `name_required`（仅当名单里存在没登记 IP 的人时为 true）、不回名单。

### 6.3 建库引擎

**扫描**：遍历选中文件夹，跳过 `~$*`、`.git`、`System Volume Information`、`$RECYCLE.BIN`、隐藏/系统目录、`node_modules`。识别扩展名：`.doc/.docx/.wps/.ppt/.pptx/.dps/.pdf`（其余跳过并计入统计）。

**体检（关键设计）**：首次建库前，抽 200 个文档试读前 4 字节：
- `PK03 04` / `D0CF11E0` / `%PDF` → 明文，可走快路径；
- `17DA5FA0` → 加密；
- 读失败（ACCESS_DENIED/0 字节）→ 记为"本机策略阻止"。
体检结论写进"体检报告"展示给库主人（"本机可直读 12%，已切换为 Office 转换模式"），**不猜、不静默**。

**转换矩阵**（每份文档按体检结果选路）：

| 类型 | 明文 | 加密（`17DA5FA0` 或读失败） |
|---|---|---|
| `.docx` | `python-docx` 直读 | Word/WPS COM → `WordOpenXML` → python 重建 docx → `python-docx` |
| `.doc` | Word COM → `WordOpenXML` → 重建 → 解析 | 同左（COM 对 `.doc` 同样适用） |
| `.pptx/.ppt/.dps` | `python-pptx` / KWPP COM | KWPP（或 PowerPoint）COM 逐页取形状文本与表格 |
| `.pdf` | `pymupdf` 抽文本（扫描件无文本层则记"需 OCR"，本轮先跳过） | ① 本机有 Adobe Acrobat → Acrobat 取文本（**待验证**，见 10.S2）② 否则解临时副本（见 6.6）→ `pymupdf` → 用完即删 |
| `.wps` | COM（WPS Writer）| 同左 |
| `.xls/.xlsx/.et` | **本轮不转换**（跳过并计入统计） | 同 |

**COM 使用规则（踩坑清单，必须实现）**
- 用 `DispatchEx('KWPS.Application')` / `Word.Application` 起独立实例，`Visible=False`、`DisplayAlerts=0`。
- 每次 `Documents.Open(..., ReadOnly=True, AddToRecentFiles=False)`；取完 `WordOpenXML` 立即 `Close(False)`；一批处理完 `Quit()`。
- **单文档超时 120 s**（大报告 + 慢机器），超时即杀 Office 进程并记失败，不阻塞队列。
- 打开带口令/受保护的文档会弹密码框 → 需先设置窗口级超时检测并强制结束；此类文档记"需口令"。
- 批处理串行（一个 Office 实例按序处理），避免多实例抢焦点、弹窗叠罗汉；后台线程优先级降到 BELOW_NORMAL。
- 只处理"新增或 src_mtime/src_size 变化"的文档（增量）。

**产物**：`<库目录>/md/<相对路径>.md`（frontmatter 记 `source_path`）+ 索引库 `<库目录>/library.db`。
- 落 md 的理由：`/api/tables` 要按文档取表格正文、也要给溯源路径。
- 磁盘足迹：md 是明文的（python 写）；索引 `documents.content` 也是全文。这两者都要在向导里明说（见 6.6）。

**索引**：沿用现有 schema 与分词（jieba + `build_match_query`，AND→OR 降级，`bm25(fts,10,1)`）。每库独立 sqlite，规模几百–几千篇，索引几十 MB。

### 6.4 检索服务（沿用 `share_server.py` 并扩充）

只读接口（均带可选 `?name=` 标识调用者）：

```
GET /                  服务说明（无敏感信息）
GET /api/health        在线/版本/篇数/最后更新（供中心与客户端探活）
GET /api/meta          库名、库主人、共享范围、篇数、端口
GET /api/stats         统计
GET /api/search?q&dir&limit    检索（limit ≤ 30，片段 48 token）
GET /api/tree?path=    子目录聚合（来自索引，不读磁盘）
GET /api/list?path=    目录内文件列表（≤500）
GET /api/tables?path=  该文档全部表格（GFM/HTML）
```

保留现有实现里的这些执行细节：`rel_path` 覆盖索引两步查询（避免 2 GB 表扫超时）、`LIKE ... ESCAPE`、`decode_param` 的 UTF-8/GBK 双编码兼容（Git Bash 下 curl 传中文会变 GBK）、按 IP 滑动窗口限流（默认 60 次/分钟）、JSONL 审计、`Cache-Control: no-store`、响应不含 `source_path`。

### 6.5 权限模型

- 库端配置 `allow_cidrs`（默认 `["10.91.0.0/16"]`），可选叠加 `allow_people`（姓名→IP，沿用现有 `share_people.json` 语义）。
- 三个预设：`全院（默认）/ 名单内 / 仅本机`。
- 拒绝返回 `403`（越权）与 `401`（姓名未登记）区分开；UI 上"暂停共享"只是把 `allow_cidrs` 清空，不删索引。
- 中心**不存权限、不代理请求**，因此权限只有一个执行点（库端），不会出现"中心说可以、库说不可以"的分裂。

### 6.6 数据足迹与合规边界（必须向库主人明说）

1. 索引 `library.db` 的 `content` 字段含**文档全文明文**；`md/` 目录也是全文明文。两者都落在库主人自己机器上。向导第二屏用一句话讲清，并给"仅存片段（前 N 字，默认 20000、可配 `snippet_only_chars`）+ 不落 md"的收紧开关（默认关）。**实施取舍（2026-11-17 库主人决定）**：召回优先、外泄控制放松，片段长度默认给足 20000 字，不为防外泄牺牲检索能力；该开关本身必然损失截断之外的召回，属知情选择，不推荐默认开启。
2. 加密 PDF 兜底路径：解到 `%TEMP%\LanDocShare\` 的**副本**，抽完文本立即删除，不保留明文 PDF。
3. 服务端只输出片段与表格，不提供全文/下载；审计日志本地保留 30 天。
4. **不合规红线**：`acrobat.exe` 兜底只在"本机没有 Adobe Acrobat 且该 PDF 读不了"时触发；工具随安装包分发这件事需要库主人知情并承担（此决策由库主人做出，风险已在讨论中告知）。

### 6.7 后台调度
- 建库任务在**用户空闲时**推进（判据：最近 5 分钟无键鼠输入，或当前用户已锁屏）——避免同事在用电脑时被 Office 实例拖慢。
- 每轮批处理完写检查点（`meta.last_scan_ts`），断电/重启后接着干。
- 托盘气泡提示：首轮完成时提示"已收录 N 篇，可被检索"。

## 7. 登记中心（registry）

- 单文件服务（同一个 exe 的 `LanDocShare.exe --registry` 模式，或独立 `registry.py`），默认端口 8767，与现有 8766 互不影响。
- 数据：内存字典 + 落盘 `registry.json`（原子写）；条目 `{name, ip, port, lib_name, doc_count, version, last_seen, status}`。
- 接口：
  - `POST /register`（库软件每 60 s 心跳，含篇数）→ 返回中心时间与"是否需要升级"。
  - `GET /libraries` → 在线库清单（TTL：5 分钟内有心跳 = 在线；30 分钟无心跳 = 移除）。
  - `GET /health` → 中心自身状态。
- 安全：只接受 `10.91.0.0/16` 来源；不接受来自客户端自报的 IP（用连接对端 IP）；不做鉴权（内容只有元数据，泄露无害）。
- 客户端缓存：skill 把上次拿到的库清单写 `~/.pi/skills/lan-lib-search/cache_libraries.json`（24 h）；中心不可用时用它 + 逐库 `/api/health` 探活。

> **实施补充（2026-11-17）**：落地为 `landoc/registry.py`，两种起法 `python -m landoc.registry` 或 `python -m landoc.cli registry`（打包版 `LanDocShare.exe registry`），默认 8767、状态文件 `~/.landoc-registry/registry.json`，`--state-dir` / `--allow-cidrs` 可改；`/libraries` 条目另带 `age_seconds`、`online`、`url`，并按"在线优先 + 名字"排序。库端在 `Config.registry_url`（`init --registry-url`）非空时，由 `LibraryApp` 起一条 `landoc-heartbeat` 线程：启动即报一次、之后每 60 s 一次，中心不可达就跳过该轮（不影响本库检索）；状态窗口多一行「登记中心」（已登记 · 中心时间 / 连不上）。中心自身用 `--install-autostart` 写 `HKCU\...\Run` 的独立值名 `LanDocShare-registry`，与库软件的 `LanDocShare` 互不影响。客户端缓存改到 `%LOCALAPPDATA%\lan-lib-search\cache_libraries.json`（skill 目录可能只读），中心不可用时**逐库探活**再降级使用。

> **实施补充（2026-11-17，名单分发）**：设计里"库主人维护一份全部门名单、同事客户端拉取"落成中心的两个端点：`POST /roster`（正文是 `姓名,IP,部门` CSV，**只接受中心所在机器的来源 IP**——`roster_admin_ips` 默认取本机所有 IP 加回环，避免任何同事都能改全院名单；落地 `<state-dir>/roster.csv`，`--roster` 可改）与 `GET /roster.csv`（网段内任何人可取）。说明页展示"已发布 N 人 + 部门分布 · 更新于 …"。库软件侧由 `landoc/roster.py`（`Roster` 把"人 + 部门"绑在一起；拉取/发布/CSV 校验/按部门排序）与 `landoc/roster_ui.py`（授权名单窗口：姓名/IP/部门三列、增删改、导入导出、从中心拉取时可选合并或整体替换、发布到中心）实现，"保存"直接写 `allow_people` 与 `people_departments` 并即时生效；命令行等价物 `people --pull` / `--publish` / `--dept`。

> **实施补充（2026-11-17，部门列）**：`Config.people_departments: {姓名: 部门/备注}` 只用于分组查看、不参与授权（授权仍只看 `allow_people` 里的 IP）。窗口按"部门 → IP"排序，没填部门的沉底；写入配置时会剔除已不在名单里的孤儿项；CSV 第三列可省，没有部门信息时导出仍是两列（老文件不受影响）。

## 8. 客户端 skill（`lan-lib-search`）

两个动作：**列库** 和 **查库**。

```
用户："查一下院里有没有马斯京根的资料"
→ 1. 读缓存/拉中心名单（在线 N 个库）
→ 2. fan-out：并发 12 路，每库 GET /api/search?q=马斯京根&limit=8&name=<我>，单库超时 2 s
→ 3. 合并：按 score 归一到各库最大值 × 库级权重；同一库内按原顺序；截取前 20
→ 4. 输出：按库分组列出（库主人 · 文档标题 · 相对路径 · 片段），失败库单独一行注明"未响应"
→ 5. 用户追问某篇的表格 → GET /api/tables?path=...&name=<我>
```

细节约定：
- 首次使用问"你在共享资料库登记的名字"，写 `identity.txt`（一行 UTF-8），之后静默复用。
- 用户可指定"只查某人/某个库"，也可"全院一起查"；默认全院。
- 部分库超时**不报错**，用"在线 X/Y 个库返回结果"的脚注交代清楚。
- 单次查询词 ≤ 3–4 个；命中率低时提示换更短的词（沿用现有 skill 的话术）。
- 输出**必须**带"来自谁的库 + 文档路径"，便于线下溯源（不提供原文）。

> **实施补充（2026-11-17）**：落地为 `skill/lan-lib-search/`（`SKILL.md` + `scripts/query.py`，仅标准库）。四个命令：`libs` / `search` / `tables` / `whoami`。因为授权已改成**按 IP 放行**（§6.2 实施补充），姓名不再是必填——`identity.txt` 只在库返回 `401 name required` 时才需要（`whoami --set 姓名`）；`401 ip not registered` 直接提示"让库主人把 IP 加进名单"，不猜名字。`config.json` 支持 `{"registry": "..."}` 与 `{"weights": {"陈鋆": 1.3}}`，环境变量 `LANLIB_REGISTRY` 优先级最高。无 Python 时的 curl 降级路径直接写进 `SKILL.md`，由 AI 逐库查后自行合并。
